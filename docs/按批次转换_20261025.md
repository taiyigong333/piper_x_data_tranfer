## 执行设计与接口

- 复用转换器：`/home/cv/gcj/project/data_transfer/to_pi/code/piperx_to_openpi_vla/convert.py`，未改源码。
- 本次入口：`/home/cv/gcj/project/data_transfer/to_pi/code/scripts/convert_pi_batches_20261025.py`。本地副本位于 `remote_changes/scripts/convert_pi_batches_20261025.py`。
- 解释器：`/home/cv/gcj/project/data_transfer/to_dynamic_vla/code/.venv/bin/python`。`to_pi/code/.venv` 缺少 cv2；因此复用已有完整转换环境，没有修改或重装原环境。
- 四个批次并行，批次内按路径排序，episode 索引各自从 0 开始。拒绝覆盖已存在的 batch 目标。
- 输出 30 Hz，两路 RGB（`camera_front`、`camera_wrist_right`）等比例缩放并居中黑边至 224×224，视频为 MP4。
- state 为 `[x, y, z, rx, ry, rz, gripper]`；action 为下一帧实际反馈 state，最后一帧重复末帧，沿用现有项目定义。
- 时间对齐沿用现有转换器：等长 `_align` 优先，否则按相机时间戳插值 raw 状态。
- 仅对新输出规范化元数据：补齐五个标量 feature，state/action 的 names 使用一维列表，episode 的 tasks 使用指令列表。依据 [LeRobot v2.1 官方实现](https://github.com/huggingface/lerobot/blob/v0.3.3/src/lerobot/datasets/utils.py)。

启动前通过 4 个现有测试函数（图像黑边、状态插值、语言覆盖与空指令拒绝）以及独立的正向轨迹发现检查。原有 discovery 测试的期望顺序是 `[forward/..., episode_1/forward/...]`，与转换器按路径排序的约定相反，因此原测试会失败；未修改该测试，用独立检查验证实际排序和反向排除。

1. 源文件转换前后 size、mtime_ns、SHA256 一致，保存 episode 索引至源文件的清单。
2. 每条 Parquet 的 state 与源对齐状态逐元素一致，action 与下一帧 state 定义一致；全部数值有限、维度及 float32 类型正确。
3. episode、frame、全局 index 连续，task_index 全为 0，时间轴为 30 Hz；tasks 和 episodes 指令全部一致。
4. 每条轨迹的两路视频全部解码，核对 224×224、30 Hz、帧数及总视频文件数。

输出追溯文件：每个 batch 的 `meta/source_manifest.json`（源路径、SHA256、长度等）与 `meta/conversion_validation.json`（统计与核验结论）。
